# Blocked roadmap items

Items here require external state or an operator decision and are not active implementation work.

- P0: Repeatable cold-load test under installed Tampermonkey and Violentmonkey on current Chrome/Edge and Firefox. Blocked because no manager installations, browser profiles, or configured test browsers are available in this checkout; automating installation would require external software/profile setup.
- P1: Verify logged-in account, subscription, and moderation surfaces. Blocked because this workspace has no authenticated Kick session, and testing those controls requires an account owner to provide a logged-in browser context.
- P1: Scrub stitched ad ranges from the HLS manifest. Blocked by the measured IVS WASM/blob-worker path: the manifest is not visible to the page realm, and worker injection into the opaque WASM pipeline is unverified and playback-critical. (2026-08-16: superseded for observability by R-09: the IVS Web Player SDK emits first-party ad-break events, a read-only path that needs no worker injection. Manifest *scrubbing* stays blocked; ad-break *observation* moved to ROADMAP R-09.)
- P1: R-45, wire `@downloadURL`/`@updateURL` so the userscript can auto-update. **Operator decision, not a technical blocker.** The old blocker is gone: the repo is public as of 2026-08-17, so a raw HTTPS URL would resolve. What remains is that shipping one points an update channel at every installed copy on end users' machines, which is the same class of decision the roadmap already defers under "Publishing to a userscript catalog or extension store without explicit approval". Two things an agent cannot settle: the GitHub token in use cannot read `two_factor_authentication` (it returns null), so hardware-key 2FA on the publishing account cannot be confirmed from here; and the distribution-channel-takeover evidence gathered 2026-08-18 (the Feb 2025 Greasy Fork inactive-account compromise injected payment-scraping code into two live userscripts) makes this worth an explicit sign-off rather than a default. On approval the work is small: a raw URL pinned to a tag rather than a moving branch in `src/metadata.txt`, plus a sha256 `update_hash` in the Firefox `updates.json`. (Moved from ROADMAP 2026-08-18.)

- P2: R-50, show an unresolved prediction against its 24-hour refund deadline. **Blocked on an external condition that cannot be created here: a live channel with an active prediction.** Measured 2026-08-18. The endpoint does exist and is in contract: a channel page calls `GET https://kick.com/api/v2/channels/{slug}/polls` itself, and it answers **200** with `{status, data}`. But `data` was **null on 33 of 33 live channels** harvested from Kick's own browse grid, so the payload shape has never been observed. No prediction-specific endpoint exists to fall back on: `kick.com/api/v2/channels/{slug|id}/predictions` answers **405**, and `web.kick.com/api/v1/{channels/{id}/polls, channels/{id}/predictions, predictions/{id}}` all **404**. Two further unknowns that the item's own evidence conflates: Kick ships *Polls* (a chat multiple-choice vote) and *Predictions* (points wagering with the 24-hour auto-refund) as separate features, and it is unverified whether `/polls` carries predictions at all; the 24-hour refund clock is documented only in the help article, never seen in a payload. Writing a normaliser and a countdown against an unseen shape would produce code that passes its own invented tests and fails on real data: the same failure R-49 was reverted for. **To unblock:** capture one real `/polls` body while a prediction is running (the channel's own broadcaster can start one, or watch a large channel until one appears), then confirm whether it carries stake/outcome/created_at fields and a resolution deadline. (Moved from ROADMAP 2026-08-18.)

- P3: R-55, bring the four loyalty systems into one view. **Blocked on an authenticated Kick session.** This is the same blocker that already holds the Drops panel and the logged-in verification item, which the item's own acceptance half-anticipated by excluding Drops. Measured signed out against a live channel, 2026-08-18: **every one of the four progressions is per-account and gated.** `GET kick.com/api/v2/channels/{slug}/points` is **401**, `channels/{slug}/me` is **401**, `web.kick.com/api/v1/gamification/collectibles` is **403**, and the Daily Rewards affordance this build already drives is Kick's own header button, which is **not rendered at all when signed out** (`rewardButtonPresent: false`). Kick Levels is worse than gated: no endpoint for it has been *discovered*, and four plausible spellings (`/api/v1/levels`, `/users/me/levels`, `/gamification/me`, `/gamification/daily-rewards`) all answer **404**, so even finding the right read requires watching what a signed-in page fetches. The only two loyalty-shaped endpoints that answer anonymously are `channels/{slug}/leaderboards` (200) and `web.kick.com/api/v1/kicks/{id}/leaderboard` (200). Both are channel-wide *gift* leaderboards, not the viewer's own points or level, so they cannot stand in. Building against unobserved shapes is what R-49 was reverted for, and the live gate runs logged out so none of it could be exercised here even if written. **To unblock:** use the same signed-in browser context the other authenticated items need. Record what the page fetches for Levels and Channel Points, then the panel is ordinary work. (Moved from ROADMAP 2026-08-18.)

- **A live-gate pass that runs signed in.** Everything entitlement-related is unit-tested against captured shapes and was measured by hand against a real account, but the live gate runs anonymous, so no automated check exercises the authenticated catalog, `/me`, or the collectibles read the bearer fix repaired. Blocked on an operator decision about credentials in a test run: the item's own text said so and pointed here, so it was leaving the active roadmap looking like work rather than a decision. It would now also cover R-55's four loyalty progressions and R-28's Drops panel, which are blocked on the same session. (Moved from ROADMAP 2026-08-18.)

Everything needed is in place: the ranked list, the trigger, and the plain-name insertion boundary. This is a sign-off, not an implementation. (Split from ROADMAP R-25 on completion, 2026-08-16.)
